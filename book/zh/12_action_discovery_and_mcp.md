# 第12章 行动发现、MCP 与生物学工具生态

## 12.1 Agent 怎样知道自己能做什么

如果你只给模型一个问题，却没有提供任何工具清单，它可能会根据记忆说出软件名称，但并不知道当前环境是否安装、版本是否兼容、输入是否满足要求。知道某个工具存在，与当前能够正确使用它，是两种知识。

行动发现就是为任务寻找可能的工具、数据库和操作方式。Biomni 的研究把生物医学行动空间的整理作为重要组成部分：从文献中发现工具与资源，再通过统一环境支持任务规划和代码执行。[R06] 本书借鉴的是“先建立可用能力地图”的原则，而不是简单复制工具数量。

一个可用能力地图应包含工具功能、输入输出、适用范围、安装状态、测试状态和权限。它既供模型检索，也供程序检查。

## 12.2 工具目录不是软件名字大全

设目录里有三个工具，都声称能进行“功能分析”。一个做基因集富集，一个做微生物通路定量，一个做蛋白功能注释。仅凭描述中的关键词，模型可能选错。目录应使用更具体的任务类型与输入类型。

可以把工具发现分为两步：先根据任务语义召回候选，再根据硬条件过滤。硬条件包括物种、数据类型、矩阵阶段、计算资源和许可证要求。若没有候选满足条件，应返回“当前没有合适工具”，而不是选择最接近的名字。

```json
{
  "tool_id": "pseudobulk_sum",
  "task_type": "aggregate_raw_counts",
  "input_type": "cell_by_gene_counts",
  "requires": ["donor_id", "cell_type"],
  "output_type": "donor_by_gene_counts",
  "network": false,
  "writes_files": false,
  "validation_status": "tested_on_synthetic_data"
}
```

这个条目明确了工具做什么，也明确了测试范围。不能把“在合成数据上通过测试”改写成“经过真实临床数据验证”。

## 12.3 MCP 解决连接方式，不解决科学正确性

Model Context Protocol 提供一种连接模型应用与外部能力的协议。可以把它理解为一种标准化插座：客户端发现工具、读取资源或获取提示模板，服务端提供相应能力。协议减少重复适配，但不保证工具适合当前研究问题。[R11]

MCP 工具可以包含行为注解，例如是否只读、是否可能产生破坏性修改、是否与开放外部环境交互。这些注解是提示信息，不是安全保证；不可信服务端可以提供错误声明，客户端仍需要自己的权限和风险控制。[R11]

因此，不应把“支持 MCP”当成科研可靠性的证书。一个通过 MCP 暴露的差异分析工具，仍然可能使用错误的分析单位；一个返回结构化数据的数据库，仍然可能含有过时注释。

## 12.4 客户端、服务端与宿主应用

宿主应用负责管理用户任务、模型连接、权限和状态。客户端负责与某个服务端通信。服务端提供具体工具或资源。把这几层分开，可以避免将外部工具获得的材料自动提升为宿主规则。

例如服务端返回一段论文摘要，摘要只是数据。它不能要求宿主泄露密钥、改写任务目标或调用另一个写入工具。模型可能同时看见任务指令与外部文本，因此应用层必须保持来源边界。

对于本书的教学项目，不需要先搭建完整 MCP 服务。可以先实现本地工具契约，再为稳定工具增加协议适配层。这样学习重点仍然放在正确的输入、输出和验证，而不是通信细节。

## 12.5 新工具进入系统的验证流程

引入一个新工具，可以依次检查来源可信度、文档完整性、输入输出契约、最小运行例子、失败行为和权限范围。只有这些条件明确后，才让 Agent 在自动模式中选择它。

最小测试不应只有正常输入。应包括空文件、错误物种、缺失元数据、超大输入、网络失败和输出不完整。对于有写入副作用的工具，应在隔离目录中测试，并确认不会越过工作区。

工具版本更新后，应重新运行关键测试。即使函数名称未变，默认参数或返回结构也可能变化。工具目录中的版本与测试时间，应随更新一起维护。

## 12.6 发现能力与执行能力分离

一个 Agent 可以提出“这个任务可能需要某种单细胞模型”，但在软件未安装、数据条件不满足或权限不允许时，它只能生成建议，不能记录成已执行。能力状态可以分成 `known`、`available`、`validated` 和 `authorized`。

这四种状态回答不同问题：是否知道该工具、当前是否可调用、是否在目标范围内通过测试、当前任务是否获准使用。只有四者都满足，才应进入自动执行路径。

对公开教学仓库，这种区分也能防止 README 夸大能力。列出“计划接入的工具”不等于已经实现适配，更不等于已经运行完整分析。功能表应把实现状态写清楚。

## 12.7 一个实用的发现策略

先建立几十个高质量工具条目，比抓取几千个未验证名称更有价值。每个条目应包含一个成功例子、一个失败例子和一个明确边界。然后根据真实任务记录扩充目录，优先解决反复出现的能力缺口。

模型可以帮助从文档提取候选契约，但最终契约必须通过程序或人工验证。自动发现的内容仍是待审核资料，不应直接成为可执行权限。

## 12.8 练习与参考思路

**练习一：**服务端声称工具只读，但实际会上传数据。参考思路：注解不能代替行为检查，应限制网络、审查实现并要求数据外发批准。

**练习二：**系统发现一个新工具，但未安装，报告应怎样写？参考思路：写成候选工具或建议步骤，明确未执行；不能生成看似真实的输出文件路径或结果。

**本章要点：**行动发现建立候选能力，验证和授权决定是否可执行；协议标准化不等于科学可靠性。
