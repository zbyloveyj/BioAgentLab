# 第8章 工作流运行时：依赖、并行与恢复

## 8.1 为什么需要运行时

当项目只有两个函数时，你可以直接顺序调用。但当任务包括检索、多个数据处理步骤、模型评审和报告生成时，就需要一个运行时来决定哪些任务可以执行、哪些必须等待、哪些已经失败。

运行时不是语言模型。它负责维护任务依赖、状态和资源，并把需要语义判断的问题交给模型。这样可以把“理解任务”与“保证执行秩序”分开。成熟科学工作流工具也强调依赖、缓存与可重复执行；本书借鉴这些原则，而不尝试用聊天循环替代所有工作流系统。[R18]

## 8.2 用有向无环图描述依赖

如果 B 必须使用 A 的输出，就存在 A→B 的依赖。多个任务形成有向无环图，即 DAG。无环很重要：如果 A 等 B、B 又等 A，两个任务都无法开始。

MicroMetaCell 的一个小图是：元数据审计同时解锁微生物表检查和代谢物表检查；两者都通过后才能检查配对；配对通过后才能计算样本级关系；单细胞数据审计可以并行进行，但跨组学整合必须等待全部前置条件满足。

```text
metadata_audit
    |           
    +--> microbiome_audit --+
    |                       +--> pairing --> association
    +--> metabolome_audit --+
    |
    +--> singlecell_audit ------> host_summary

association + host_summary --> evidence_report
```

图中箭头代表数据或前提依赖，不代表生物学因果关系。这两个意义应在图例中明确区分。

## 8.3 最小拓扑执行器

下面的教学代码每次选择前置依赖已完成的任务。真实运行时还需要更多状态与异常处理，但基本思想并不复杂。

```python

def execution_order(dependencies: dict[str, set[str]]):
    known = set(dependencies)
    for name, parents in dependencies.items():
        if not parents <= known:
            raise ValueError(f"Unknown dependency for {name}")
    done = set()
    order = []
    while len(done) < len(dependencies):
        ready = sorted(
            name for name, parents in dependencies.items()
            if name not in done and parents <= done
        )
        if not ready:
            raise ValueError("Dependency cycle detected")
        for name in ready:
            done.add(name)
            order.append(name)
    return order
```

这里采用排序，使相同图产生稳定的执行顺序。确定性不是所有 Agent 决策都必须具备的性质，但对纯依赖解析而言，它可以减少不必要的差异。

## 8.4 并行不是越多越好

两个互不依赖的检索任务可以并行；需要同一文件独占写入的任务则不应随意并行。外部服务还可能有速率限制，即使本地有很多线程，也不能无限增加请求。

并行执行需要考虑资源：CPU、内存、网络连接、磁盘和模型调用额度。一个单细胞矩阵可能占用大量内存，同时启动多个处理任务会导致全部失败。资源需求应作为任务元数据，而不是事后猜测。

对模型评审而言，并行多个角色也不等于获得独立判断。它们可能共享同一个基础模型、同一提示词结构和同一偏差。并行可以降低延迟，但不能自动增加科学证据数量。

## 8.5 缓存键应该包含什么

如果输入文件、参数和工具版本没有变化，可以复用已通过验收的结果。但缓存键若只包含文件名，就可能把新数据误认为旧数据。合理的缓存键应包含输入摘要、参数、工具版本以及必要的参考数据库版本。

```python
import hashlib
import json


def cache_key(input_hash, params, tool_version, db_version):
    payload = {
        "input_hash": input_hash,
        "params": params,
        "tool_version": tool_version,
        "db_version": db_version,
    }
    text = json.dumps(payload, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(text.encode()).hexdigest()
```

模型调用的缓存还应考虑模型标识、提示词版本和检索材料。若只是希望复现同一已生成输出，可以直接缓存原结果；若希望评估模型随机性，则不能把缓存结果当成一次新的独立运行。

## 8.6 任务失败后的传播

如果一个前置任务失败，下游任务不能继续假装拥有有效输入。应将其标记为阻塞，并说明缺少哪个依赖。对不依赖该步骤的支线，可以继续执行，以保留部分有用结果。

这种“局部失败、明确降级”的设计，比要么全部重来、要么全部继续更合理。例如配对检查失败后，仍然可以完成各组学的数据审计和文献证据整理，但不能输出配对关联分析。最终报告应区分已执行与因依赖失败而跳过的部分。

报告生成器本身也应受到约束：它只能读取已经验收的产物，以及明确标记的失败记录。不要让模型从一张计划清单推断所有任务都已经完成。

## 8.7 工作流的测试层次

单元测试检查一个函数，例如依赖图是否能检测环。集成测试检查几个模块是否正确衔接，例如工具输出能否写入证据台账。端到端测试检查从输入到报告的完整路径。三者回答不同问题，不能互相替代。

一个有价值的端到端测试应故意加入错误输入，例如重复样本标识、缺失受试者信息或无效证据编号，并要求系统拒绝错误结论。只测试“正常输入得到报告”，无法发现很多科研风险。

测试报告也要区分“程序按预期拒绝”与“程序崩溃”。前者可能是正确行为，后者可能是工程缺陷。用统一失败率把两者混在一起，会误导评价。

## 8.8 练习与参考思路

**练习一：**两个任务都向 `report.json` 写入结果，应如何处理？参考思路：给每个任务独立产物路径，再由汇总任务合并；或采用事务和锁。不要依赖执行时机碰巧不冲突。

**练习二：**数据库更新，但原始样本文件未变，缓存是否还有效？参考思路：若输出依赖数据库内容，应使数据库版本进入缓存键；否则相同输入可能需要重新分析。

**本章要点：**运行时管理执行秩序；依赖图不是因果图；缓存、并行与恢复都需要明确条件。
