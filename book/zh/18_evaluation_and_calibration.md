# 第18章 评价：系统到底有没有变得更可靠

## 18.1 先定义成功，再选择指标

“回答看起来不错”不能作为科研 Agent 的唯一成功标准。不同任务需要不同指标：文献任务重视召回与引用支持，工具任务重视选择与执行，统计任务重视方法适配与数值正确，假设任务重视可检验性与证据边界。

评价应同时考虑成功、正确拒绝和错误成功。输入无效时拒绝分析，是正确行为；输出一份完整但建立在错误样本配对上的报告，是危险的错误成功。把两者都只按“是否完成报告”计分，会奖励不可靠系统。

本书的测试分成程序正确性、流程正确性和科学适用性。前两者可以通过大量确定性测试覆盖；第三者通常需要领域专家和真实任务评估。

## 18.2 分层指标

输入层检查数据审计是否发现错误。检索层检查相关材料是否被找到。证据层检查引用是否真实支持陈述。工具层检查调用和参数是否合适。报告层检查结论是否超出证据。每层都有独立分母，不能随意混算。

例如引用有效率可以定义为有效来源标识数除以全部引用数；但这只检查存在性。引用支持率还需要判断来源是否支持对应陈述。一个系统可能所有 DOI 都真实，却把文献含义全部说反。

对拒答行为，可以记录覆盖率与选择性风险：系统在多少问题上给出实质答案，给出答案的问题中错误比例多少。始终拒答可能风险低，但没有实用价值；始终作答可能覆盖高，却误导严重。

## 18.3 校准与 Brier 分数

若系统输出概率，就需要检查概率是否与实际频率对应。对于二分类任务，Brier 分数为预测概率与真实标签的均方误差：

$$\operatorname{BS}=\frac{1}{n}\sum_{i=1}^{n}(p_i-y_i)^2.$$

```python
import math


def brier_score(probabilities, labels):
    if len(probabilities) != len(labels) or not labels:
        raise ValueError("Mismatched or empty inputs")
    for p, y in zip(probabilities, labels):
        if not math.isfinite(p) or not 0 <= p <= 1:
            raise ValueError("Invalid probability")
        if y not in (0, 1):
            raise ValueError("Invalid label")
    return sum((p-y)**2 for p, y in zip(probabilities, labels)) / len(labels)
```

Brier 分数同时受区分能力与校准影响，不能单独完整描述系统。概率校准还需要足够样本和独立评估。模型自报“95%确信”并不会自动获得概率含义。

## 18.4 构建评估集时避免泄漏

开发集用于调整提示词、工具和规则；测试集用于最终评估。反复查看测试失败再针对性修改系统，会逐渐把测试集变成开发集。需要保留新的独立评估，尤其当你声称泛化能力时。[R17]

生物学任务还要按研究或供体划分，而不是把同一研究中的相似问题随机分到两侧。否则模型可能通过共享资料或模板获得不现实的优势。真实文献时间也可以成为划分边界，用较新的研究检验系统是否能正确利用外部证据。

评估集应覆盖阴性、冲突、缺失、实体歧义和工具故障，而不只包含容易回答的正面问题。否则系统会在最需要谨慎时失去可靠性。

## 18.5 与什么基线比较

至少考虑一个固定 workflow、一个单模型检索系统和一个不使用复杂多角色的版本。若多智能体系统只比“完全不检索的随意回答”更好，不能说明复杂架构本身有价值。

比较应尽量控制模型、检索语料、任务预算和评估标准。更大预算可以带来改进，但应明确代价。可以同时报告固定成本下的质量，以及达到相同质量所需的成本。

消融实验用于去掉某个模块，观察功能变化。例如去掉证据核验后，未知引用率是否上升；去掉反思后，方法错误是否增加。消融不应只比较总分，还要看该模块本来负责的错误类型。

## 18.6 人工评审的设计

专家应使用明确评分表，并尽可能不知道系统版本。对存在主观判断的任务，可以让多位评审独立评价，再检查分歧。分歧不是必须消除的噪声，有时反映任务本身存在合理不确定。

评价假设时，可以要求评审指出最强支持、最关键空缺和是否值得下一步验证，而不是只给1到10分。结构化理由有助于分析系统到底哪里改进。

模型评审可以用于初筛和规模化检查，但不应成为唯一最终标准，尤其当生成与评审使用相同模型时。要警惕语言风格、长度和术语密度影响评分。

## 18.7 报告评价结果的边界

合成数据上的测试证明程序在这些输入下按预期运行，不证明真实研究任务有效。小型人工问题集上的高分，也不能自动推广到所有疾病或组学。报告应给出样本范围、任务类型、失败案例和未覆盖条件。

一个诚实的结果表会同时展示成功数、拒绝数、失败数和未测试项。不要把未测试写成零错误，也不要把无法联网的适配器声称为已完成端到端验证。

## 18.8 练习与参考思路

**练习一：**系统引用编号全部有效，但其中一半不能支持句子，应该报告什么？参考思路：来源有效率高，引用支持率低；两个指标分别记录。

**练习二：**多Agent比单Agent更好，但调用次数增加十倍，如何解释？参考思路：报告质量与成本共同变化，补做预算匹配比较；不能把全部收益归因于角色划分。

**本章要点：**评价应奖励正确拒绝并惩罚错误成功；科学适用性、程序通过率和模型偏好分数不是一回事。
