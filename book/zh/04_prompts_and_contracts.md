# 第4章 提示词不是咒语：把任务写成契约

## 4.1 从模糊请求到可执行任务

“分析这些数据，给我一个有意义的结果”是一条自然的请求，但不是足够明确的执行规范。模型不知道研究单位是什么、允许使用哪些数据、哪些分析已经预先指定、哪些输出需要人工批准。缺失的约束会被模型自行补全，而补全往往看起来合理。

更好的任务说明应包含目标、输入、输出、约束和验收标准。例如：“读取经过脱敏的样本表，检查样本标识唯一性与缺失字段；不进行差异检验；输出 JSON 格式的数据审计报告；发现重复标识时停止。”这条任务并不华丽，却可以直接转成程序检查。

本书把提示词看作人机接口的一部分，而不是保证正确性的魔法。提示词告诉模型应该怎样做，代码则检查它是否真的满足要求。两者缺一不可。

## 4.2 把事实、要求和材料分开

一个研究调用可以分为三个区块。规则区说明行为边界；任务区说明当前目标；材料区提供待分析内容。材料中的论文摘要、网页文本和工具输出可能包含任意文字，不能因为其中出现“忽略此前规则”就获得指令权限。

例如你要求模型从文献摘录中提取证据，材料区可能包含作者的推测、编辑文字或恶意插入内容。系统应把它们当作数据，而不是执行命令。这个问题将在安全章节进一步讨论。

一个简洁的任务模板如下。注意，要求输出证据标识，而不是让模型自由编造参考文献。

```text
任务：核对一条生物学陈述。

规则：
仅使用下面提供的证据记录。
证据不足时输出 insufficient。
不要添加未提供的文献编号。

待核对陈述：{claim}

证据记录：
{evidence_records}

输出字段：
verdict, evidence_ids, limitations
```

## 4.3 结构化输出解决什么问题

结构化输出让程序更容易解析模型结果，但不能自动解决事实错误。一个格式完全正确的 JSON 仍然可能包含不存在的证据、方向相反的关系或无依据的高置信度。必须分别检查语法、字段和语义。

语法检查回答“是不是有效 JSON”；字段检查回答“是否存在必要键、值的类型是否正确”；语义检查回答“引用的证据是否存在、是否适用于当前陈述”。只有前两层正确，不足以生成科研结论。

```python
import json

ALLOWED = {"supported", "contradicted", "insufficient"}


def parse_verdict(text: str, known_ids: set[str]):
    obj = json.loads(text)
    if not isinstance(obj, dict):
        raise ValueError("Expected an object")
    if obj.get("verdict") not in ALLOWED:
        raise ValueError("Invalid verdict")
    ids = obj.get("evidence_ids")
    if not isinstance(ids, list):
        raise ValueError("Expected evidence list")
    if not all(isinstance(x, str) for x in ids):
        raise ValueError("Evidence IDs must be strings")
    if not set(ids).issubset(known_ids):
        raise ValueError("Unknown evidence ID")
    return obj
```

这个函数仍然没有核对证据含义。下一层需要检查每条证据是否真正支持当前 claim。不要把“成功解析”记录成“成功验证”。

## 4.4 好的约束应该可以测试

“像一位顶尖专家一样认真”很难验收。“每条结论必须包含至少一个有效证据标识，并明确研究对象和研究类型”则更容易检查。前者可以作为风格提示，后者才是可靠系统的骨架。

但约束也不能机械化。例如强制每条结论都必须有引用，可能促使模型给无证据结论添加无关引用。更合理的规则是：事实性结论必须有支持材料；缺失材料时允许输出空证据列表，但 verdict 必须是 `insufficient`。验收规则应该鼓励诚实，而不是鼓励把表格填满。

同样，“必须给出三个新机制”可能诱导系统凭空创造。应允许有效候选少于三个，并说明原因。数量目标与科学质量发生冲突时，不能让数量成为硬性优先级。

## 4.5 示例驱动与边界样本

少量示例可以帮助模型理解输出形式，但示例必须覆盖失败和不确定情况。只展示成功案例，会让模型以为所有任务都应该得到肯定结论。对于证据核验，至少应包括支持、冲突、信息不足和来源不适用四种情形。

以“细胞 C 表达受体 R，因此代谢物 M 激活了该细胞”为例，参考输出应指出：受体表达最多支持潜在响应能力，不能单独证实配体存在、有效暴露或信号激活。这个例子把科学边界写进了任务，而不只是规定 JSON 形状。

示例中不能放入真实敏感数据，也不应使用测试集答案。提示词开发本身是一种模型选择过程；反复根据最终测试集修改示例，会让测试不再独立。

## 4.6 逐步任务比一次写完整报告更可检查

一个长提示词要求模型同时做检索、统计、解释、引用和写作，很难定位错误。可以拆成“提取 claim”“查证据”“核对适用范围”“生成报告”几个阶段，每一阶段有独立的输入与验收规则。

拆分也有代价：阶段之间可能丢失信息，调用次数增加，错误可能被中间摘要压缩隐藏。因此应把关键对象通过结构化字段传递，而不是只传一段自然语言总结。最重要的 claim、来源、版本和限制，应在整个流程中保持标识一致。

这不是要求所有问题都建立复杂流水线。简单任务仍应简单处理。拆分的理由应是提高可检查性，而不是让架构图显得更复杂。

## 4.7 提示词版本管理

把提示词保存在文件中，并记录版本或内容哈希。一次实验更换了模型、提示词和检索语料三个因素，却只记录模型名称，将无法解释性能变化来自哪里。

建议建立一个小型回归集：空输入、缺失字段、中文术语、别名冲突、证据方向相反、无效引用和恶意材料。每次修改提示词都运行这些案例，观察是否修好了一个问题却破坏了另一个问题。

一个实用的验收顺序是：先检查输出能否解析，再检查引用存在，再检查任务规则，最后进行专家语义复核。不要在前面已经失败时继续计算漂亮的平均评分。

## 4.8 练习与参考思路

**练习一：**改写“帮我查这个菌的功能”，使其成为可执行任务。参考思路：明确菌的稳定标识、菌株范围、需要哪类功能证据、允许的数据库、返回字段，以及无法识别实体时如何停止。

**练习二：**模型输出支持性结论，但引用记录标记为动物研究，而问题针对人群因果效应。应该怎样处理？参考思路：语法可能正确，但适用范围不匹配。可保留为机制线索，不能直接标记为人群因果证据。

**本章要点：**提示词说明任务，程序执行约束；结构化输出保证可解析，不保证事实正确；高质量示例必须包括失败与不确定性。
