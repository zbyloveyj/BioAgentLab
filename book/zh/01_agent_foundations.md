# 第1章 从问答工具到科研智能体

## 1.1 一个问题为什么不能只回答一次

设想你向系统提出：“请判断某个微生物是否可能通过一种代谢物影响特定免疫细胞。”聊天模型可以立即生成一段解释，但完成研究任务需要先确认许多事实：微生物标识是否正确，代谢物究竟是哪一种化学实体，样本来自哪里，细胞信息是否来自同一组受试者，以及问题中的“影响”指关联还是干预效应。

这些事实不全在提示词中。系统必须采取行动来补充信息，并根据新信息改变下一步。这种围绕目标、状态、行动和反馈组织起来的过程，就是本书讨论的 Agent。它不一定必须使用多个模型，也不一定每一步都自主决定；自主程度是设计变量，不是越高越好的指标。

普通问答通常可以表示为“输入→回答”。科研 Agent 则是“观察→选择行动→执行→检查结果→更新状态”。输出有时是一句话，有时是一条检索请求，有时是一个等待人工批准的执行计划。ReAct 将推理与外部行动交替组织，是理解这种循环的一个经典入口。[R02]

## 1.2 五个不能混淆的组成部分

**目标**描述最终希望解决什么问题。**状态**记录当前已知信息与任务进度。**策略**根据状态选择下一步行动。**工具**将行动转为可执行的操作。**环境反馈**告诉系统执行后实际发生了什么。这五个概念不是产品组件清单，而是一种分析系统的方法。

以文献检索为例，目标是找到某条关系的原始研究；状态包括已经搜索的词、命中文献、尚未覆盖的人群；策略决定扩大检索还是阅读全文；工具向数据库发送请求；反馈是返回记录或错误。把“检索结果为空”看作反馈，与把它解释成“关系不存在”，是两件完全不同的事。

记忆是在不同步骤或任务之间保留的信息。长期记忆不是 Agent 的必备条件：一个只运行十步、使用当前状态完成任务的程序仍然可以具有智能体性质。相反，一个保存所有聊天记录的应用，也可能只是被动问答工具。判断系统时，应看行动是否由反馈驱动，而不是看宣传图上有几个模块。

## 1.3 用研究助理作类比

把语言模型看作刚进入课题组、阅读能力很强但容易把猜测说成事实的研究助理。你不应该允许他凭记忆填写实验结果，也不应该因为他会解释统计学，就不再检查数据和软件参数。你会给他任务书、原始资料、软件、记录模板和升级求助的规则。

这些安排分别对应任务规范、外部知识、工具接口、运行日志和人工复核。类比的价值在于帮助理解责任分工，但不能把模型当作真的具有经验、责任意识或独立实验能力的人。软件系统的行为由模型输出、程序控制和环境权限共同决定。

当助理说“我已经分析完成”，你首先应该问：“输出文件在哪里？对应哪一个输入版本？”当 Agent 说同样的话，程序也应检查文件存在、格式有效、任务状态与执行结果一致，而不把一句自然语言声明当成完成凭证。

## 1.4 Workflow 与 Agent 不是对立关系

固定 workflow 适合规则明确、输入稳定的步骤，例如读取表格、检查样本标识、计算指定变换。Agent 适合需要在不确定条件下选择行动的部分，例如判断证据空缺后应该查哪一种来源。两者组合往往比完全自由的 Agent 更实用。

例如一个单细胞处理任务可以规定“必须先保存原始计数，再做归一化”。这条科学与数据管理约束不应交给模型随意改写。模型可以在发现异常时建议检查双细胞、样本污染或批次效应，但建议进入执行之前仍要经过预设规则。

因此，本书采取“受约束的自主性”：允许系统在明确边界内选择动作，把不可违反的规则写入代码。不要把“让模型决定一切”误认为更先进。对可重复分析而言，不必要的自由度往往增加调试成本。

## 1.5 一个最小循环

下面的示例不是完整框架，而是把 Agent 的基本控制逻辑压缩到可以阅读的程度。`policy` 负责决策，`tools` 负责执行，`state` 负责记录结果。

```python
from dataclasses import dataclass, field

@dataclass
class State:
    goal: str
    observations: list[str] = field(default_factory=list)
    done: bool = False


def run(state, policy, tools, max_steps=8):
    for step in range(max_steps):
        action = policy(state)
        if action["name"] == "finish":
            state.done = True
            break
        name = action["name"]
        if name not in tools:
            raise ValueError("Unknown tool")
        result = tools[name](**action["arguments"])
        state.observations.append(str(result))
    return state
```

这里最重要的不是 `for` 循环，而是三个边界。第一，工具必须在注册表中，不能因为模型说出了名字就执行。第二，步骤数有限，避免反复搜索却永不停止。第三，观察结果必须来自工具实际返回，而不是模型自己声称执行成功。

这个短程序还有明显缺陷：没有参数校验、超时、错误分类、证据标识和任务恢复。后续章节会逐一补上。理解为什么缺这些东西，比直接复制一个庞大框架更有助于形成工程判断。

## 1.6 科研能力的三个层次

第一层是**完成操作**，例如程序成功读取文件。第二层是**完成分析**，例如统计方法与实验设计匹配。第三层是**支持结论**，例如证据确实允许当前解释。第一层成功不能自动推出第二层，更不能推出第三层。

假设一个工具把一万个细胞都作为独立重复，得到极小的 P 值。程序可能没有任何报错，但分析单位可能不对。再假设每位受试者都有正确的 pseudobulk，差异分析也合理，结果仍不能单独证明微生物导致了该细胞变化。科研 Agent 必须在三个层次分别设检查点。

这也是为什么本书不把“调用工具成功率”当成唯一评价标准。一个系统应同时记录操作完成率、方法适配性、证据支持程度和无法作答的情况。允许正确停止，是可靠性的组成部分。

## 1.7 练习与参考思路

**练习一：**任务是“把某个数据目录中的 FASTQ 文件生成质控报告”。哪些部分需要 Agent，哪些部分适合固定 workflow？

参考思路：文件发现、命名校验、软件执行和输出检查可以固定化。异常文件解释、根据质量问题建议后续分析可以由模型协助。若输入和质控标准早已明确，整个任务甚至可以不需要 Agent。不要为了使用新技术而引入不必要的决策环节。

**练习二：**检索工具返回零条记录，系统应输出“没有证据”还是“关系不存在”？

参考思路：首先只能说当前查询未检索到记录。应检查检索词、数据库覆盖和接口状态，再区分“没有检索到”“研究没有发现效应”和“有证据反对”三种情况。后三者在科学含义上不同。

**本章要点：**Agent 是反馈驱动的行动系统；可靠性来自明确边界；执行成功、分析合理和结论成立需要分别验证。
