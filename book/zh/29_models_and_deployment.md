# 第29章 模型接入、成本与部署

## 29.1 业务逻辑不要绑在一个供应商上

研究流程需要的是生成候选、提取结构或比较材料的能力，不应该在每个函数中直接写死某个模型API。把供应商调用放到适配层，研究模块只依赖一个小接口，便于测试、替换和控制数据流。

最小接口可以是 `complete(prompt) -> str`；更成熟的接口还应返回使用量、请求标识、停止原因和错误类型。工具调用与结构化输出的具体格式可能不同，因此适配层还负责转换，而不是让所有科研模块理解每家服务的消息结构。[R20,R21]

```python
from typing import Protocol

class TextModel(Protocol):
    def complete(self, prompt: str) -> str:
        ...

class OfflineModel:
    def complete(self, prompt: str) -> str:
        return '{"status": "synthetic_demo"}'
```

离线模型不是用来模拟真实智能水平，而是让测试能够稳定触发不同流程分支。它的输出应始终标为教学或测试，不能混入真实证据。

## 29.2 外部服务调用的最小保护

模型名称、密钥和超时从配置读取。密钥不写入仓库；模型标识由使用者根据实际可用服务指定，而不是在教材中永久固定一个可能变化的名称。调用前应确认数据允许发送到该服务。

适配器应检查响应状态、输出类型和大小，并处理限流、超时与服务端错误。不要在失败时返回一个看似合理的默认答案，否则Supervisor无法区分模型判断与基础设施故障。

本项目提供可选的外部文本模型适配入口，默认离线运行。没有密钥、没有网络或未获授权时，不调用外部服务。测试使用本地响应样例，不把未执行的在线调用声称为已验证。

## 29.3 模型选择由任务评价决定

提取字段、阅读长文、选择工具和比较假设可能需要不同能力。可以使用便宜模型处理简单结构任务，再把困难判断交给更强模型，但路由规则需要评估。

更大模型不一定在每个任务都更可靠，较小模型也不应因为便宜就承担超出能力的关键判断。评价应使用自己的任务、资料与验收标准，而不是只看通用排行榜。

模型路由还会改变可复现性。报告应记录每个步骤使用的模型与参数，避免只写一个总的模型名称。

## 29.4 成本预算不只看token

总成本可能包括输入输出token、检索服务、专业计算、存储和人工复核。多角色辩论容易增加调用次数，因此应先确定哪些比较值得做，再分配预算。

可以设置每任务调用上限、累计token上限、最大执行时间和最大重试次数。费用估计应使用实际服务的当前计价配置；本书不写死价格，也不把本地估计当成最终账单。

```python
from dataclasses import dataclass

@dataclass
class Budget:
    limit: int
    used: int = 0

    def consume(self, units=1):
        if type(units) is not int or units < 0:
            raise ValueError("Invalid budget units")
        if self.used + units > self.limit:
            raise RuntimeError("Budget exhausted")
        self.used += units
```

这个计数预算用于教学动作次数。真实系统应分别管理不同资源，而不把所有消耗压缩成一个没有单位的数。

## 29.5 从命令行开始部署

一个可靠命令行程序应接受明确参数，创建独立输出目录，失败时返回非零退出状态，成功时说明产物位置。相比先建立复杂网页界面，命令行更容易测试与复现。

本书的入口使用 `python -m bioagent`。离线演示、测试和可选联网检索分为不同命令，避免读者运行教程时意外产生费用或外发数据。输出目录已存在时应拒绝覆盖，除非用户显式指定覆盖选项。

以后接入网页、任务队列或服务API时，核心逻辑仍应保持独立。界面负责收集参数与展示结果，不应隐藏权限和分析选择。

## 29.6 可观测性应该回答具体问题

当用户说“为什么没有结果”，日志应能回答：任务在哪一步、哪个工具失败、是否预算耗尽、哪些产物已经保存。只有最终异常堆栈，不足以理解一个多阶段研究任务。

可以记录每一步的耗时、输入摘要、输出状态和来源标识，但不记录敏感全文或密钥。对模型调用，保留简短决策摘要比保存大量不可核验的自由思考更有用。

运行指标应服务于改进：重复检索比例高，可能需要更好的状态；工具选择错误多，可能需要更明确的契约；引用错误多，则应加强证据层，而不是只换模型。

## 29.7 版本更新与回滚

更新模型、提示词、检索语料或工具后，应运行回归集。若出现明显退化，应能够回到上一个版本，并保留变化说明。不能仅因为新版本名称更新，就默认它对研究任务更合适。

发布版本应包含源码提交、构建记录和测试范围。测试通过不表示没有任何缺陷，但它让使用者知道哪些行为确实检查过。

## 29.8 练习与参考思路

**练习一：**外部模型超时，适配器返回“没有发现相关证据”，为什么错误？参考思路：它把网络故障伪装成科学结论，应返回结构化错误并保留未完成状态。

**练习二：**网页显示成功，但没有输出文件，部署层应怎样处理？参考思路：成功由产物验收决定，不由界面或模型的一句话决定。

**本章要点：**供应商适配、预算与可观测性独立于科研逻辑；默认离线与明确授权减少误操作。
